# COORD account database

Apply `migrations/202609210001_coord_accounts.sql`, then `migrations/202609210002_coord_cloud.sql`, once and in order. The migration is atomic. Supabase Auth owns Google sign-in for this deployment; configuring Google OAuth credentials and allowed redirect URLs is a separate operator step. The website presents Google as its only sign-in method. The second migration adds durable shared source, agent presence, file leases and staged atomic publications. Set `COORD_STORAGE_MODE=supabase` on Vercel for HTTPS collaboration without a separate hub.

All tables have RLS enabled with no anonymous or authenticated policies or table grants. The public API RPCs revoke default public execution and grant execution only to `service_role`. Keep the service-role secret on Vercel (and the hub only for legacy hub deployments), never in the browser or desktop bundle. The Vercel handler must verify a browser token using Supabase Auth `getUser` before supplying `p_user_id`; the database deliberately trusts that service-only parameter. Device authentication instead uses a random 256-bit token passed as `p_device_token`. Only its SHA-256 digest is persisted. Never supply both identities.

`coord_account_api(p_action,p_user_id,p_device_token,p_payload)` returns the normal route body, or `{error,status}` for expected failures. Supported actions are `workspace`, `project_create`, `project_get`, `invitation_create`, `invitation_accept`, `member_remove`, `device_revoke`, `device_start`, `device_poll`, `device_approve`, `connect`, and `logout`. Project actions take `projectId`; member removal adds `userId`; connect/revoke add `peerId`; project/device creation take `name`; redemption takes `key`; pairing takes `deviceCode` or `userCode`. `connect` requires a paired desktop token and returns `{ok:true,project:{id,name}}` after recording its binding. HTTPS clients then use `coord_sync_api`; legacy hub clients obtain a hub invitation. Browser logout must also sign out through Supabase Auth.

`coord_peer_authorized(p_project_id,p_peer_id)` returns a boolean. The hub must check this on every account-backed peer operation and fail closed if the database is unavailable. `coord_cloud_project` has the same arguments and returns `{id,name,allowed:true}` only for a live authorized binding; otherwise it returns null. Do not treat a previously successful lookup as lasting authorization. Device revocation deletes the entire desktop session and all its project bindings. Member removal removes that project's bindings and outstanding invitations.

The early-testing quotas are 20 total projects, 5 owned projects per account, 30 members/invitations per project, 30 live desktop sessions per account, 20 project/device bindings per account, and 200 pending pairings. Pairing expires after 10 minutes, membership invitations after one day, and desktop sessions after 30 days. A transaction-scoped advisory lock serializes account operations across serverless workers, including quota checks, one-use redemption, logout, and connect. This intentionally favors correctness at early-testing scale. Rates are 600 calls/minute globally, 120 authenticated calls/minute/account, 30 pairing starts/minute globally, 30 polls/minute/device code, and 10 approvals/minute/account. Auth login/provider rate limits remain managed by Supabase Auth.

Run `pnpm exec vitest run tests/supabase-accounts.test.ts` for disposable native PostgreSQL tests. They create minimal Supabase Auth tables and roles, apply the complete migration, and verify permissions, concurrent one-use redemption, device scope, membership removal, and session revocation. A passing local test is not proof that the production migration or OAuth configuration has been deployed.

## Configure authentication and Vercel

For this COORD deployment, the Supabase origin is `https://vlydsenwhvrnwuodgdgo.supabase.co` and the website origin is `https://coord-startup-control-plane.vercel.app`.

1. In Supabase Authentication → URL Configuration, set the Site URL to the website origin. Allow `https://coord-startup-control-plane.vercel.app/api/account/callback` and `https://coord-startup-control-plane.vercel.app/api/account/callback?state=*`. The wildcard only covers the state on this fixed origin and path; the server checks the random state against its HttpOnly cookie before exchanging a code.
2. Set `COORD_AUTH_MODE=google` on Vercel. This rejects the website's email/password login and registration endpoints. Disable the Email provider and leave unrelated providers disabled in Supabase Authentication → Sign In / Providers so direct Supabase API calls cannot offer another sign-in method. Google-only sign-in does not require SMTP.
3. For Google, create a Web application OAuth client in Google Cloud. Use the website origin as its authorized JavaScript origin and `https://vlydsenwhvrnwuodgdgo.supabase.co/auth/v1/callback` as its authorized redirect URI. Configure the consent audience appropriately. Google exempts sign-in requests limited to basic name, email and profile scopes from the test-user-list requirement, even while the app is in Testing; additional scopes can introduce restrictions. Supply the client ID and secret under Supabase Authentication → Sign In / Providers → Google, enable it, and leave nonce and email checks enabled. Use only basic identity scopes (openid, email, profile).
4. Save `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, and `COORD_WEBSITE_URL` in the Vercel project's Production environment. Set `COORD_GOOGLE_ENABLED=1` only after Google is configured. Redeploy. Keep the secret value in Vercel's Secret type, never in a public-prefixed variable or source file.
5. Check `/api/account/config`, then verify `authMode:google`, a real Google login and project creation. Desktop pairing can be tested now; connecting a cloud project folder requires the second migration and HTTPS mode described in [the deployment guide](../docs/vercel-early-testing.md).

Legacy backend deployments can omit `COORD_AUTH_MODE` to retain their existing email/password or username/password APIs; the current website deliberately has no password form or configuration-failure fallback. Google remains visibly unavailable until `COORD_GOOGLE_ENABLED=1`.

The local `web:dev` command currently targets the legacy loopback hub. Test the Supabase flow on a configured HTTPS deployment because it uses Secure, host-only cookies and an exact HTTPS origin.

References: [Supabase Google login](https://supabase.com/docs/guides/auth/social-login/auth-google), [Google audience rules](https://support.google.com/cloud/answer/15549945), [redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [API keys](https://supabase.com/docs/guides/api/api-keys).

## Shared source API

`coord_sync_api(project_id,peer_id,session_id,device_token,operation,input)` is service-role only. It validates the live hashed device token, current membership and exact device/session binding on every operation. Vercel validates safe paths, UTF-8, size and credential-like content before forwarding uploads. SQL also enforces paths, bytes, quotas and revision hashes. The operations are `manifest`, `read`, `heartbeat`, `reserve`, `release`, `stage`, `commit`, `abort`.

A publication stages up to 50 files, then atomically verifies all reservations and base hashes before replacing canonical source. Any stale file rejects the entire publication. Reservations expire after 120 seconds and agent heartbeats renew them; staged uploads expire, and revoked bindings invalidate their agents and publications. Account revocation and publication use the same transaction lock, so concurrent requests cannot bypass revocation.

The early beta caps canonical content at 500 files/16 MiB per project, 1 MiB per file, and canonical plus staged payloads at 256 MiB across the installation. Database overhead and backups require additional capacity. The operator can read stored source. RLS does not make server-readable source end-to-end encrypted.

Run `tests/cloud-sql.test.ts`, `tests/cloud-flow.test.ts` and the native cloud tests for disposable SQL and composed HTTP/native tests. They do not replace a real hosted login and two-computer acceptance check.
