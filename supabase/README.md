# COORD account database

Apply `migrations/202609210001_coord_accounts.sql` once to an empty Supabase project. The migration is atomic. Supabase Auth owns email/password and Google sign-in; configuring Google OAuth credentials and allowed redirect URLs is a separate operator step. These tables store account/project/device metadata, not source files. The persistent hub stores each project's shared source and remains necessary for collaboration.

All tables have RLS enabled with no anonymous or authenticated policies or table grants. The three RPCs revoke default public execution and grant execution only to `service_role`. Keep the service-role secret on Vercel and the hub, never in the browser or desktop bundle. The Vercel handler must verify a browser token using Supabase Auth `getUser` before supplying `p_user_id`; the database deliberately trusts that service-only parameter. Device authentication instead uses a random 256-bit token passed as `p_device_token`. Only its SHA-256 digest is persisted. Never supply both identities.

`coord_account_api(p_action,p_user_id,p_device_token,p_payload)` returns the normal route body, or `{error,status}` for expected failures. Supported actions are `workspace`, `project_create`, `project_get`, `invitation_create`, `invitation_accept`, `member_remove`, `device_revoke`, `device_start`, `device_poll`, `device_approve`, `connect`, and `logout`. Project actions take `projectId`; member removal adds `userId`; connect/revoke add `peerId`; project/device creation take `name`; redemption takes `key`; pairing takes `deviceCode` or `userCode`. `connect` requires a paired desktop token and returns `{ok:true,project:{id,name}}` after recording its binding. Vercel then obtains the actual connection invitation from the hub. Browser logout must also sign out through Supabase Auth.

`coord_peer_authorized(p_project_id,p_peer_id)` returns a boolean. The hub must check this on every account-backed peer operation and fail closed if the database is unavailable. `coord_cloud_project` has the same arguments and returns `{id,name,allowed:true}` only for a live authorized binding; otherwise it returns null. Do not treat a previously successful lookup as lasting authorization. Device revocation deletes the entire desktop session and all its project bindings. Member removal removes that project's bindings and outstanding invitations.

The early-testing quotas are 20 total projects, 5 owned projects per account, 30 members/invitations per project, 30 live desktop sessions per account, 20 project/device bindings per account, and 200 pending pairings. Pairing expires after 10 minutes, membership invitations after one day, and desktop sessions after 30 days. A transaction-scoped advisory lock serializes account operations across serverless workers, including quota checks, one-use redemption, logout, and connect. This intentionally favors correctness at early-testing scale. Rates are 600 calls/minute globally, 120 authenticated calls/minute/account, 30 pairing starts/minute globally, 30 polls/minute/device code, and 10 approvals/minute/account. Auth login/provider rate limits remain managed by Supabase Auth.

Run `pnpm exec vitest run tests/supabase-accounts.test.ts` for disposable native PostgreSQL tests. They create minimal Supabase Auth tables and roles, apply the complete migration, and verify permissions, concurrent one-use redemption, device scope, membership removal, and session revocation. A passing local test is not proof that the production migration or OAuth configuration has been deployed.

## Configure authentication and Vercel

For this COORD deployment, the Supabase origin is `https://vlydsenwhvrnwuodgdgo.supabase.co` and the website origin is `https://coord-startup-control-plane.vercel.app`.

1. In Supabase Authentication → URL Configuration, set the Site URL to the website origin. Allow `https://coord-startup-control-plane.vercel.app/api/account/callback` and `https://coord-startup-control-plane.vercel.app/api/account/callback?state=*`. The wildcard only covers the state on this fixed origin and path; the server checks the random state against its HttpOnly cookie before exchanging a code.
2. Keep email confirmation enabled. Supabase's default email service restricts recipient addresses and sending rates; configure your own SMTP provider before inviting arbitrary testers. Confirmation can complete sign-in in the original browser for up to one hour. If that browser session expires, confirm the email and then sign in with the password.
3. For Google, create a Web application OAuth client in Google Cloud. Use the website origin as its authorized JavaScript origin and `https://vlydsenwhvrnwuodgdgo.supabase.co/auth/v1/callback` as its authorized redirect URI. Configure the consent audience appropriately; an app in Testing needs test users. Supply the client ID and secret under Supabase Authentication → Sign In / Providers → Google, enable it, and leave nonce and email checks enabled. Use only basic identity scopes (openid, email, profile).
4. Save `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, and `COORD_WEBSITE_URL` in the Vercel project's Production environment. Set `COORD_GOOGLE_ENABLED=1` only after Google is configured. Redeploy. Keep the secret value in Vercel's Secret type, never in a public-prefixed variable or source file.
5. Check `/api/account/config`, then verify a real email or Google login and project creation. Desktop pairing can be tested now; connecting a cloud project folder requires the separately deployed hub described in [the deployment guide](../docs/vercel-early-testing.md).

The local `web:dev` command currently targets the legacy loopback hub. Test the Supabase flow on a configured HTTPS deployment because it uses Secure, host-only cookies and an exact HTTPS origin.
